## N103：旧保存结果误结束新一次保存

原来只用导出包 ID 匹配原生保存回执。同一份 ZIP 在请求断线后重新保存时，第一次保存的迟到结果仍能命中新监听器：旧成功会显示旧路径并释放当前包；旧取消或失败也会提前结束新等待，解除编辑器和关闭按钮的忙碌保护。

现在每次打开保存窗口都生成独立的 `requestId`。桌面桥校验后原样交给宿主；宿主在成功、取消和错误三种结果中都带回这个标识。界面同时核对保存请求和导出包的身份，只有当前尝试的回执才能完成保存状态。ZIP 的任务 ID 保持不变，重试复用已经准备好的包。

私有 `POST /__desktop/export` 需要 `{ id, requestId }`，保存请求标识为标准小写 UUID；缺失或格式错误返回 400，不发出原生保存事件。既有会话、来源校验及任务过期的 410 保留。文件名继续来自服务中的导出任务，忽略请求体提供的文件名。

## 复现与验证

新增 [7 个场景](../scripts/tests/export-bridge.test.mjs)，最终测试文件在隔离副本中回放发布版网页控制器和桌面桥：6 项失败、1 项兼容场景通过；修复后全部通过。

- 断线后重试同一 ZIP，旧尝试分别返回成功、取消或失败；新保存继续等待、不释放包、不解除忙碌，当前结果到达后才完成。
- 缺少保存请求标识、不同请求或不同导出包的结果不能结束当前保存。
- 当前原生结果先于 HTTP 确认到达时仍可完成；旧 HTTP 确认随后失败，不影响下一次保存及监听器。
- 真实 HTTP 会话交接同一个 ZIP 的两次独立请求，事件保留对应标识；客户端文件名无法替换服务记录。
- 无会话、错误来源、无效请求和已过期任务被拒绝，修正后的有效请求可以重试；ZIP、原正文与素材保持原字节。
